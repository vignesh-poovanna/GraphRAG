Fault Handling and Safe Mode Transition

Flight software on the onboard computer continuously evaluates telemetry against expected nominal ranges. When a parameter drifts or crosses a limit repeatedly, the software escalates through a defined sequence rather than reacting to a single bad sample, which keeps the spacecraft from over-reacting to noise while still catching a genuine fault before it becomes serious. This document walks through that escalation logic and the fault severity levels it maps to.

Fault Detection Logic

Each telemetry parameter is checked on every sample against its nominal range. A single out-of-range sample increments a per-parameter fault counter rather than triggering an immediate response; only once that counter reaches a configured threshold does the flight software treat the condition as persistent rather than transient noise. Persistent faults trigger safe mode, which points the spacecraft at the sun to protect power generation and disables non-essential loads until an operator can review the situation during the next ground contact.

Fault Severity Levels

Not every anomaly warrants the same response. Flight software classifies faults into severity levels so that a minor, self-recoverable issue doesn't trigger the same drastic response as a subsystem-threatening one.

Severity LevelExample TriggerAutomated Response
Level 1 — InformationalSingle out-of-range telemetry sampleLog only; no action taken
Level 2 — WarningFault counter below safe-mode thresholdLog and continue monitoring at increased sample rate
Level 3 — CriticalFault counter reaches threshold (e.g. battery voltage, wheel temperature)Enter safe mode; sun-point and shed non-essential loads
Level 4 — EmergencyHardware watchdog timeout, processor unresponsiveHardware reset / power-cycle of the onboard computer

Recovery

Once in safe mode, the spacecraft holds a stable, power-positive attitude and waits for ground contact rather than attempting to self-diagnose further, since diagnosis usually benefits from a human reviewing the accumulated fault log alongside broader telemetry trends. During the next pass, operators review what tripped the fault counter, decide on a corrective action — anything from adjusting a threshold that was set too tight to commanding a specific subsystem workaround — and uplink a recovery command that returns the spacecraft to nominal operations. This same escalation pattern, driven by telemetry and fault counters rather than single-sample triggers, is what allowed operators to catch and manage the reaction wheel degradation described in the mission case study well before it became a more serious failure.
